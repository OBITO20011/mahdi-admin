# إعادة استخدام محرك تسليم الطلب واستئنافه

إنجاز جزئي، لا جاهزية نهائية لشاشة الطلب أو المرحلة 2.

- أصل العقد يُقرأ من `orders.operation_id → business_operations.operation_type`:
  `lite1_guest` للمسار المبسّط، و`phase3_customer_reservation_v1` للمسار الكامل.
  لا يُستدل من السلة أو الوضع الحالي. بيانات الطلب/العملية الغائبة تمنع التوجيه.
- `runCustomerV2AdminAction` نفسه يحتفظ بالطلب والوضع عند أول محاولة؛
  نفس Web Lock والتحقق من المستخدم والبصمة والحالة والمفتاح والمبالغ تبقى.
  full لا يضيف حقلاً ولا يغيّر اسم RPC أو معاملاته. lite يوجّه إلى الكاتب
  الموازي بمعاملاته، دون تمرير مفتاح الوضع للكاتب أو إنشاء محاولة جديدة عند التعافي.
- قبول/تغيير حالة lite يستخدم الكاتب الموازي مع مفتاح حتمي لكل مستخدم/طلب/حالة؛
  إعادة الضغط بنفس البيانات تعيد نتيجة واحدة، وتغيير الملاحظة لا يتجاوز ختم الطلب.
- نتيجة التسليم الجديدة تحمل UUID عملية محفوظاً داخل نتيجة المحاولة الخاصة
  المختومة؛ هذا ليس ادعاء وجود عملية جديدة في `public.business_operations`.
  إلغاء lite يصرّح `reservation_state=not_tracked` وreleased=0؛ لا يدّعي فك حجز.
  مدقق full يرفض نتيجة lite، ومدقق lite يرفض نتيجة full.

الدليل المحلي: 58 وحدة + الأنواع وstrictlint. أربع مقارنات تسليم فعلية
كاش/CliQ/دين/جزئي عبر محول TypeScript نفسه إلى PostgreSQL219/180، مع JSON
مالي ومجمل درج مطابقين للمسار الكامل. فقدان رد فعلي بعد الالتزام أُعيد بنفس
الجسم والمفتاح والمسار دون كتابة ثانية؛ نتيجة نجاح محفوظة لا تستدعي RPC جديداً.
اختبارات التزامن والحالة وCliQ والزيادة والإلغاء و628/636 وintegrity=0 محفوظة؛
network=0 وcleanup=true. `LIFECYCLE_ADAPTER_PASS.json` خارج المستودع.

14 حالة Chromium/WebKit ناجحة بلا retries: التنسيق القائم بين نافذتين،
الانقطاع/الإغلاق/الانتظار، وحالة lite الجديدة بعد إعادة التحميل بنفس الطلب
والمفتاح، ثم الإلغاء المصرّح بأنه بلا تتبع حجز.

المتبقي: ربط دليل الطلب والاسم/العنوان المقترح والتوفر في شاشة الطلب كاملةً،
بدء التوصيل ووقته، واجهة المرتجع واستئنافها، وبقية المرحلة/الفحص الكامل/CI.
