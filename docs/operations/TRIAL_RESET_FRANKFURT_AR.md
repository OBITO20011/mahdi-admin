تحضير بقرار المالك في 2026-10-16. لم ينفّذ الوكيل أي اتصال أو تصفير بعيد.
الأداة مقيدة بالسقف 171: 148 ملف migration فعلياً، مع الفجوات المعتمدة.

## ما يفعله المالك

1. يتأكد أن يوم التجربة انتهى وأن كل البيانات الموجودة تجريبية.
2. يغلق الواجهتين ويوقف وصول الموظفين ومستهلكات n8n والنسخ المجدول مؤقتاً.
3. ينسخ UUID حساب المالك من Authentication → Users. يجب أن يكون له profile نشط ودور owner فقط.
4. يشغّل المعاينة من جذر المستودع؛ هي أوفلاين بالكامل، بلا كلمة سر أو شبكة:

```powershell
node scripts/operations/frankfurt-trial-reset.mjs --dry-run
```

بعد مراجعة الخطة، يشغّل الأمر الهدّام بنفسه، مستبدلاً UUID فقط:

```powershell
node scripts/operations/frankfurt-trial-reset.mjs --apply --owner-id <UUID-المالك>
```

يطلب تأكيد `RESET kzevmysfydaslxcerogt` ثم كلمة سر DB مخفية في الذاكرة فقط.
المجلد الخارجي يجب أن يكون مربوطاً بفرانكفورت؛ ربط المستودع القديم والنسخ الليلي لا يتغيران.

## ما يبقى وما يُمسح

- يبقى حساب Auth المختار، وهويات دخوله وجلساته وعوامل TOTP، وprofile/دور المالك. تبقى صفوف Vault، بما فيها إعدادا `order_push_webhook_secret/url` إن وُجدا، دون استخراج plaintext. إعدادات Auth وأسرار Edge خارج نطاق التعديل.
- يبقى سجل فرع المالك المرتبط به صراحةً، بنفس UUID وبياناته، أو NULL إن لم يكن مرتبطاً. لا تحفظ بقية الفروع والمستودعات التجريبية. تزال صورة avatar القديمة لأنها قد تشير إلى ملف محذوف.
- تبقى حاوية `product-images` وإعداداتها، وتُحذف ملفاتها عبر Storage API باستخدام CLI الرسمي، لا عبر SQL. قد تبقى نسخة في كاش جهاز قديم حتى انتهاء صلاحيتها؛ الفحص يثبت حذف الأصل.
- تُمسح بيانات الأعمال كلها وحسابات Auth الأخرى، بما فيها أي حساب مالك تجريبي إضافي. لا DELETE/TRUNCATE على جداول الأعمال المحمية؛ تُحذف كائنات public ويُعاد إنشاؤها من SQL الأصلي.
- يبقى غلاف schema public وصلاحياته الافتراضية الخاصة بالمنصة؛ إسقاط الغلاف نفسه يمحوها. تُستعاد منح الكائنات المقبولة قبل التصفير بالضبط، بما فيها service_role، لا GRANT عام ولا تجاهل لفروق الصلاحيات.
- لا يُشغَّل seed.sql. صفوف الإعداد من migrations فقط: units=11، categories=12، advanced_monitoring_checks=22؛ وصف واحد لكل من advanced_monitoring_metrics/settings وbusiness_alert_settings وconfigurable_parcel_feature_settings وgo_live_setup_state وstorefront_settings وaudit_logs (سجل 034).
- الاستثناءات المرجعية الوحيدة بعد إعادة الربط: roles=1 (owner)، profiles=1، user_roles=1، وفرع المالك إن وجد. brands وwarehouses وبقية جداول الأعمال صفر. أي جدول جديد غير مصنّف وغير فارغ يُفشل الفحص.
- يبقى تريغر الإشعار D ومهام outbox الأربع inactive؛ مهمة cleanup تبقى active. تُحفظ تعريفات cron الجديدة بعد النجاح، لأن jobids تتغير، مع نسخة من التعريف السابق.
