# إصلاح استرجاع نسخة فرانكفورت214

الأساس main141d161 بعدPR27. لا اتصال بالمشروعين ولا نشر ولا قراءة أسرار المالك أو فك أرشيفه. كل الإثباتات على بيانات اصطناعية وحاويات محلية بلا شبكة.

## السبب المثبت محلياً

تسمية المرحلة القديمة `restore-complete-dump` كانت تشمل أيضاً تهيئة **بعد** pg_restore. الدالة `platformPostInitSql` كانت تشترط `search_path=net` وSECURITY DEFINER لدالتي net.http_get وnet.http_post. جرد فرانكفورت المحفوظ محلياً من verify-only214 يظهر لهما configuration=null وSECURITY INVOKER. تمريره للفحص القديم يعيد RESTORE_NET_SOURCE_PATH؛وبذلك يمكن أن يفشل الاسترجاع بـtool=docker/exitCode=null رغم نجاح pg_restore نفسه. لا يمكن حسم موضع محاولة المالك القديمة نهائياً من التشخيص العام؛هذا عيب مثبت يطابق نمطها،وليس ادعاء فحص الأرشيف الحي.

الجرد الآمن المشتق في `scripts/testing/fixtures/frankfurt214-restore-platform.json` يسجل بصمة ملف catalog-observed الأصلي وأسماء الامتدادات وإصداراتها وملكيتها فقط. الامتدادات السبعة:pg_cron1.6.4،pg_net0.20.4،pg_stat_statements1.11،pgcrypto1.3،plpgsql1.0،supabase_vault0.3.1،uuid-ossp1.1. pg_graphql وpgsodium **ليسا امتدادين مثبتين في هذا الجرد**؛وجود مخطط graphql أو مكتبة preload لا يعني تثبيت امتداد. الصورة17.6.1.158 توفر الإصدارات السبعة،وقد ثبت ذلك باسترجاع فعلي. النسخة تستخدم نفس preload الملتقط؛غياب مكتبة يمنع التشغيل ويظل إخفاقاً.

ظهر فرق مهم عن CLI:pg_net في public،وملكية pg_stat_statements/pgcrypto/uuid-ossp هي postgres. إنشاء كل الامتدادات تحت supabase_admin لا يعيد هذه الملكية وأعضاءها بدقة.

## التنفيذ الصارم

1. تُقرأ قائمة pg_restore --list،ويُحسب كل إدخال. تُستعاد المخططات أولاً،ثم تُنشأ الامتدادات بإصداراتها ومخططاتها ومالكيها الملتقطين،ثم تستعاد بقية القائمة. لا إسقاط لإدخال ولا تكرار؛3369 إدخالاً في الإثبات الكامل،11مخططاً و3358في البقية.
2. كل استدعاء pg_restore يحتفظ بـ--exit-on-error. وجود الامتداد قبل المرور الكامل مقصود؛تعريف pg_dump له يستخدم IF NOT EXISTS،ثم تُقارن نسخته ومخططه ومالكه بالضبط. لا تجاهل لخطأ ولا --no-owner أو --no-acl أو استثناء بيانات/امتداد.
3. إذا احتاج إنشاء امتداد باسم مالك غير superuser،يُرفع هذا العلم مؤقتاً **داخل الحاوية network=none فقط**،ويُعاد في finally،ثم تُقارن كل الأدوار والعضويات بعد الاسترجاع. لا UPDATE لكتالوج النظام في مسار استرجاع المالك. مواءمة كتالوج الامتدادات داخل سكربت الاختبار تخص المصدر الاصطناعي disposable فقط لمحاكاة post-init الخاص بالخدمة.
4. تُعاد إعدادات net من المصدر كما هي:INVOKER/config=null لفرانكفورت،أوDEFINER/search_path=net لصورة CLI. القيم الأخرى غير المدعومة تُرفض. المقارنة لا تتجاهل اختلاف الملكية أو body أو SECURITY أوsearch_path.
5. أسماء ومالكو event triggers/publications/subscriptions تُطابق مع TOC بعد الاسترجاع. كل أوامرها وأوامر عضوية publication تبقى في المرور الكامل. اختبار مستقل أثبت event trigger وpublication واشتراكاً معطلاً بلا slot؛لا تجربة اتصال/اشتراك خارجي أو ادعاء جرد حي لهذه الكائنات. بيانات الجرد القديم لا تتضمن كل إعدادات subscriptions،لذلك لا ندّعي مقارنة لم تكن ملتقطة أصلاً؛المقارنات الأصلية لم تُضعف.
6. تُقارن جميع الصفوف والبصمات والتسلسلات والأدوار والمنح والملكية والتاريخ وStorage وتُشغّل فحوص السلامة القائمة على النسخة المعزولة فقط.

## التشخيص وحفظ السجل

المرحلتان الآن منفصلتان:restore-complete-dump وrestore-platform-postinit،معrestore-schemas وrestore-extension-preflight للتجهيز. فشل داخلي لا يُنسب كذباً إلى Docker. تشخيص pg_restore يحفظ SQLSTATE إن توفر،وكود الخروج الرقمي،وTOC بالنوع/المخطط/الاسم فقط،وERROR بصياغة ثابتة مثل دور مفقود أو مخالفة قيد بلا قيم.

رسالة pg_restore من TOC لا تتضمن المخطط دائماً؛يُسترجع المخطط من قائمة الأرشيف بواسطة رقم الإدخال،ولا يُخمن من اسم المالك. لا arguments أوOID أوDETAIL أوCONTEXT أوSQL/COPY أوقيم مفاتيح أوكلمة مرور/passphrase في التقرير أوالطرفية.

قبل حذف الحاوية،يُقرأ ذيل /tmp/restore.log في الذاكرة. يُستخرج SQLSTATE من prefix الخادم،ثم تُحفظ **أحداث أخطاء بصياغة ثابتة فقط**؛لا نسخة نصية خام. الحفظ الافتراضي تحت:

`C:\ProgramData\NawasrahFrankfurtBackup\restore-diagnostics\restore-...\`

- pg-restore-sanitized.json
- server-tail-sanitized.json

يُضبط مجلد المحاولة أولاً ليمنح Administrators وحدهم FullControl مع قطع الوراثة،قبل كتابة المحتوى. restore-local.json يذكر موقع الملفات وlogs.saved. لا يُطبع محتواها في الطرفية. إذا تعذر حفظها،يظهرlogs.saved=false وRESTORE_LOG_CAPTURE_FAILED صراحة؛التشخيص الآمن يبقى في التقرير الأساسي. جلسة الوكيل Windows غير مرتفعة،لذا سجلت الاختبارات المحلية رفض الكتابة المحمية بدلاً من منح المستخدم صلاحية إضافية. نجاح الحفظ الخاص على Linux شرط إلزامي في CI،وأمر المالك هنا يتطلب PowerShell كمسؤول.

## الأمر التالي للمالك — بعد الموافقة والدمج وتحديث المجلد الرئيسي

**Restore فقط. لا حاجة إلى Backup جديد،ولا Setup جديد،ولا تغيير passphrase أوالأرشيف الموجود.** صيغة النسخة2 لم تتغير،والإثبات أعاد نفس الأرشيف مرتين. افتح PowerShell كمسؤول:

```powershell
Set-Location C:\Users\TOP\mahdi-admin
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/operations/frankfurt-backup-owner.ps1 -Mode Restore -Apply
if ($LASTEXITCODE -ne 0) { throw 'فشل Restore؛أرسل diagnostic وlogs.saved فقط،دون أسرار.' }
```

المتوقع ok:true،وتطابق البيانات/الأدوار/المنح/المخزون والذمم والأرباح وفق فحوص السلامة،والتاريخ حتى214 وملفاتStorage الثلاثة الخاصة بنسخة المالك. إذا ظهر إخفاق آخر،المرحلة والتشخيص والسجل المنقح الجديد يحددان موضعه؛لا ندّعي نجاح استرجاع فرانكفورت من تجربة محلية.
