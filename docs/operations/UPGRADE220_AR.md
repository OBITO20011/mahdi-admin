# ترقية 219 إلى 220 — مسودة لما بعد التشغيل فقط

**لا تُدمج ولا تُطبّق قبل التشغيل.** هذه الحزمة فوق مسودة #79. تبقى بطاقة يوم التشغيل وRESET219 ومرجع المالك الحالي كما هي. التنفيذ بقرار مستقل من المالك بعد T+2/3 وبعد أول نسخ ليلية ناجحة واسترجاع مطابق. الاختبارات المحلية ليست إذناً بالاتصال أو النشر.

220 يجمع تحسين التقرير السنوي وترتيب سجل المورد وسياسات القراءة المقاسة، ومنع طلب الضيف من تعديل بطاقة زبون قائم/عنوانه الافتراضي. لا تغيير لحساب الأموال أو المخزون أو الصلاحيات. 218 محجوزة. السقف الجديد 220/181، وصيغة الأرشيف v2؛ تدعم الأدوات نسخ 214–219 أيضاً. تفاصيل القياس والتطابق في [مسودة 220](../design/migration220/README_AR.md).

## قبل النافذة

- يثبّت المالك SHA الدمج المعتمد وCI وبصمات ملف 220 ومرجع `local-reference-through220-ready.json` ودليل الوصول 220. المرجع مستقل؛ لا تعِد تسمية مرجع 219 ولا تستبدل ملفه.
- جهّز PostgreSQL17 وDocker والمفتاح الحالي للأرشيف، ووصول جهاز بديل إلى الملفات المشفرة وتقارير الحماية. الأسرار تُدخل بالطريقة المخفية القائمة؛ لا تُكتب في أمر أو تقرير.
- خطّط لنافذة صيانة، وأوقف POS والاستيراد والأجهزة وجميع الكتابات؛ أغلق `ordersEnabled` من الإعدادات. أوقف مهام cron الست مؤقتاً بالمسار المعتمد وانتظر انتهاء حجز dispatch، وأوقف المستهلكات. سجّل حالاتها لإعادتها بعد القبول. لا تفترض أن حالة الحجز القديمة في 217 هي الحالة الحالية.
- لا تطفئ إعدادات الملخص أو تغيّر بيانات الإشعارات بغرض تمرير الفحص. الترقية تحفظها كما هي. فحص 220 يرفض مهمة إضافية أو أمراً/جدولاً/هوية مختلفة، أو cron نشطاً، أو طلبات مفتوحة، أو حجز dispatch جارياً. يُربط منفذ cron بإعداد منفذ الخادم المقروء، وليس بمنفذ مرجع Docker.

## الأوامر — PowerShell كـAdministrator

الأوامر التالية ورقة تجهيز، **لا تُنفّذ أثناء مراجعة المسودة**. استخدم المجلد الأساسي فقط بعد اعتماد ودمج الحزمة. ملفات الحالة والمرجع تبقى خارج Git.

```powershell
git pull --ff-only
npm.cmd run agent:preflight
$workdir = Join-Path $env:USERPROFILE 'NawasrahFrankfurt\nawasrah-fra-001-138'
$configPath = Join-Path $env:ProgramData 'NawasrahFrankfurtBackup\config.json'
$backupConfig = Get-Content -LiteralPath $configPath -Raw | ConvertFrom-Json
$proofDir = Join-Path $workdir ('upgrade220-protection-' + (Get-Date -Format 'yyyyMMdd-HHmmss'))
New-Item -ItemType Directory -Path $proofDir -ErrorAction Stop | Out-Null
# انسخ مرجع220 المستقل المعتمد إلى workdir وتحقق من بصمته المعتمدة قبل المتابعة.
Get-FileHash -LiteralPath (Join-Path $workdir 'local-reference-through220-ready.json') -Algorithm SHA256
& .\scripts\operations\frankfurt-backup-owner.ps1 -Mode Plan
& .\scripts\operations\frankfurt-backup-owner.ps1 -Mode Backup -Apply
$before = Join-Path $proofDir 'backup219.json'
Copy-Item -LiteralPath (Join-Path $backupConfig.backupRoot 'last-backup-status.json') -Destination $before -ErrorAction Stop
npm.cmd run frankfurt-owner-upgrade220 -- --dry-run --workdir $workdir
npm.cmd run frankfurt-owner-upgrade220 -- --apply --workdir $workdir --backup-evidence $before
```

تُرفض النسخة إن لم تكن 219/180 ومن المشروع الصحيح، أو تغيّرت بايتات الأرشيف، أو تجاوز عمرها 26 ساعة، أو اختلفت لقطة القاعدة عن اللقطة المثبتة في النسخة. النسخ الجديدة تتضمن التزاماً ببصمة دليل المصدر؛ النسخة القديمة التي لا تملكه لا تصلح لهذه البوابة: أنشئ نسخة جديدة بالأدوات المعتمدة قبل التطبيق.

نجاح apply يعني تطبيق SQL وتسجيل التاريخ والتحقق الصارم؛ **لا يعني انتهاء سلسلة الحماية**. تظهر `protectionPending=true` و`complete=false`. احتفظ بمسار `report.json` الذي طبعه الأمر؛ لا تعِد apply عند هذا التنبيه. أكمل:

```powershell
# ضع مسار تقرير apply الناجح الذي طبعته الأداة؛ لا تختَر تقرير تشغيل آخر.
$applyReport = Read-Host 'مسار report.json لتطبيق220 الناجح'
& .\scripts\operations\frankfurt-backup-owner.ps1 -Mode Backup -Apply
$after = Join-Path $proofDir 'backup220.json'
Copy-Item -LiteralPath (Join-Path $backupConfig.backupRoot 'last-backup-status.json') -Destination $after -ErrorAction Stop
& .\scripts\operations\frankfurt-backup-owner.ps1 -Mode Restore -Apply
$restore = Join-Path $backupConfig.stateRoot 'restore-local.json'
npm.cmd run frankfurt-owner-upgrade220 -- --verify-only --workdir $workdir --backup-evidence $after --restore-evidence $restore --upgrade-report $applyReport
```

لا يُعلن `complete=true` إلا بعد مطابقة أرشيف 220 نفسه ببصمته، ومطابقة كل الصفوف والتسلسلات والأدوار والعضويات والكتالوج وACL وStorage والتاريخ، وحالة pg_net الخام، ونجاح فحوص السلامة، بلا استثناءات. الاسترجاع Docker `network:none` ولا يتصل بقاعدة حية. أي كتابة بعد النسخة/الاسترجاع تبطل القبول النهائي وتستلزم نسخة واسترجاعاً جديدين.

بعد ذلك: «افحص»، افتح التقرير السنوي وسجل المورد وتحقق من طلب ضيف تجريبي تحت إشراف المالك، ثم أعد cron والمستهلكات إلى الحالات المسجّلة وتحقق من آخر تشغيل وتسليم للوجهة الصحيحة. لا تغيّر أوقات الملخص أو الوجهات. يُفتح استقبال الطلبات بعد القبول فقط.

## الفشل والتراجع

- قبل الكتابة: أصلح سبب الرفض وأعد التخطيط؛ لا تتجاوز بصمة أو اختلاف ACL/كتالوج.
- ملف 220 معاملة واحدة. عند فشلها لا يُسجَّل التاريخ. إن نجح SQL ثم فشل تسجيل التاريخ، **توقف للمراجعة**؛ لا تعِد SQL ولا تسجّل migration يدوياً لإخفاء الفرق.
- بعد تطبيق ناجح مع فشل Backup/Restore: تبقى الكتابات متوقفة والحماية غير مكتملة، ويُراجع السبب. لا تُحوِّل الفشل إلى نجاح ولا تكرر عملية بمفتاح جديد.
- لا توجد downgrade مالية آلية. التراجع الحي قرار مالك بعد تشخيص، باستخدام نسخة 219 الفاصلة وخطة الاسترجاع المعتمدة؛ لا تُسترجع فوق قاعدة حية بأداة Restore المعزول.
- RESET220 عملية إتلاف مستقلة وليست جزءاً من الترقية. لها `--plan` ثم `--dry-run` ثم `--apply` و`--resume` وحراس المالك/MFA وpg_cron والكتابات والمرجع. لا تستخدمها للتراجع بعد بدء أعمال حقيقية.

## ما يبقى يدوياً

اعتماد الدمج والتوقيت، مرجع 220 النهائي وبصمته بعد آخر دمج يغيّر مصدر الوصول، تجميد الكتابات/cron واستعادتها، إدخال الأسرار المخفي، نسخة/استرجاع صاحب المحل، فحص واجهة حقيقي والتوقيع. لا تفعّل 220 من مسودة PR، ولا تغيّر مرجع D−1 أو أدوات 219 في يوم التشغيل.

## القياس المحلي الأولي

على بيانات وهمية غير فارغة (استلام20، بيع كاش2 ودفع جزئي1، تسلسلpg_net مستعمل): Backup219 11.428s،Restore219 40.067s،apply220 مع التحقق/التسجيل25.171s،Backup220 10.811s،Restore220 35.609s،verify-only14.382s. مجموع سلسلة الحماية نحو137.5s،باستثناء تجهيز Docker والإجراءات اليدوية. هذه ليست قياساً لتوقف فرانكفورت أو لحجم أرشيفها؛يحجز المالك نافذة صيانة ويقيس نسخة أرشيفه المعزولة قبل تحديد التوقيت. رفضت البروفة مصدر نسخة خاطئاً وإعادة apply وACL وتعريفاً ومهمةcron زائدة ودليلRestore قديماً،بلا استثناءات مقارنة. اختبارRESET220 المستقل نجح محلياً في نحو415s شاملاً تجهيز الحاوية والتصفير العادي وأربع حالات انقطاع/استئناف، مع181ملفاً وصفر فروق كتالوج/ACL وثباتMFA وpg_net. حُوكي عبور UTC7→8نوفمبر في العادي والاستئناف؛ رُفضت الكتابة الخارجية المتزامنة وفقدان حساب المالك. لا يُستخدم RESET أثناء الترقية بعد بدء أعمال حقيقية.
