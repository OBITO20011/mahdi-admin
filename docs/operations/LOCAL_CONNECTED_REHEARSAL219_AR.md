- النقل لا يقبل URL؛يقبل فقط سياقاً حياً أصدره Restore نفسه،بمعرّف Docker الكامل وبصمة الأرشيف و219/180 ومشروع فرانكفورت. `WeakSet` يلغي السياق عند مغادرة callback،مع فحص network/mounts. لا يكفي إنشاء كائن مشابه أو إعادة استخدام سياق منتهٍ.
- ملفات فك الأرشيف ولقطة الاحتفاظ محمية للمستخدم الحالي/Administrators قبل الكتابة. لا Auth/MFA أو Vault خام في الأدلة؛النواة القائمة تحفظ بصماتها فقط.

- cron launcher يبقى `off` حتى عند محاكاة تفعيل صفوف cron؛لا Edge أو Telegram/Push process. القاعدة `network none`،وfetch في المنسق يقبل loopback فقط ويرفض redirects. بناء المتجر يستخدم fixture SEO loopback القائم،وليس قراءة فرانكفورت.

## الاستثناء المحدود — تبعيات الإسقاط

لا تُسقط الخطة namespace public نفسه؛لذلك لا تُعدّ تبعية امتداد على هذا الاسم سبباً لإسقاطه. جذور الفحص الآن هي نفس علاقات ودوال وأنواع خطة الإسقاط الفعلية،مع تتبع الملكية الداخلية وملكية الامتداد في الاتجاه اللازم لعدم إخفاء المالك. لا استثناء لـnet/pg_net أو schema أو امتداد؛حارس الرفض وخطة DROP كما كانا حرفياً.

اختبار PostgreSQL فعلي يرفض تبعية خارجية على جدول،وعلى دالة،وعضو امتداد تابع لكائن مستهدف،واستهداف أعضاء امتداد public،ومحاولة إسقاط امتداد. كل الحالات قبل تنفيذ DROP.

قاعدتا CI للتصفير/الاستئناف والترقية تُجهزان pg_net في public بالإصدار0.20.4 والمالك supabase_admin تماماً كجرد فرانكفورت المحلي. لا اختلاف إصدار. بعد كل تصفير واستئناف تُقارن هوية الامتداد وschema net وتواقيع/مالكي http_get/post/delete،وتنفذ http_post داخل معاملة تُعكس قبل commit إلى عنوان loopback فقط؛لا إرسال. تبقى الأرشيفات والاسترجاع الافتراضي والمقارنة الصارمة كما هي.

أثبتت البروفة الاصطناعية الخارجية وجود حاجز ملكية storage.objects أثناء020 بعد الاسترجاع؛لا يُعالج بمنح أو تخفيف. نتائج الأرشيف الحقيقي لا تُستنتج من ذلك،وتُسجّل البروفة من الخطوة الأولى بعد CI.

## محاكاة Supautils من دليل المالك المكتمل

قرار2نوفمبر:تهيئة داخل callback البروفة فقط،بعد Restore الصارم وقبل أي قطع. دليل خارجي mandatory وcomplete:true،يحوي19قيمة supautils كنصوص وsession/shared/local preload. لا إعداد افتراضي مجهول أو URL أو ملف إعداد مالك محلي. تُقارن قيم pg_settings الـ22 حرفياً بعد التحميل وبعد الاختبار السلبي.

يكتب سكربت الاختبار ملفاً مؤقتاً في /tmp/pgdata داخل الحاوية الموثقة،ويحمّل session_preload_libraries=supautils بإعادة تشغيل PostgreSQL فيها فقط. لا تعديل لـRestore العادي أو أوامر الإنتاج،ولا ALTER ROLE/SUPERUSER أو GRANT أو نقل ملكية أو عضوية.

القيم الفارغة الثلاثة تظهر فارغة في pg_settings لكنها defaults غير مضبوطة؛المكتبة ترفض كتابة placeholders='' صراحة. يُترك هذا default دون سطر ملف،ويظل الفحص الحرفي الكامل إلزامياً؛أي قيمة فعلية مختلفة تفشل.

الإثبات:CREATE ثم DROP لسياسة وهمية USING(false) داخل rollback بدور postgres NOSUPERUSER؛ثم نغيّر policy_grants وحده مؤقتاً إلى{} في الحاوية،فتُرفض العملية بخطأ الملكية؛ثم نعيد المصدر وتنجح. الكتالوج وACL والمالكون والأدوار والعضويات وبصمة بيانات الأعمال متطابقة قبل/بعد،والـcron launcher يبقىoff والشبكةnone.

المسار /etc/postgresql-custom/extension-custom-scripts موجود في الصورة المثبتة؛لم يُخلق أو يُنسخ محتوى. إن غاب،يتوقف قبل الاختبار ولا يختلق محتوى. authenticator يحتفظ بإعداد دور المصدر؛المحاكاة لا تغيّر أدوار Auth أو إعداداتها.

CI يشغّل الاختبار نفسه على أرشيف صناعي219 وقيم منصة اختبار بلا أسرار؛ذلك لا يحل محل ملف دليل المالك الخارجي أو الأرشيف الحقيقي. إعدادات Supabase local المعتادة وحزم الترقية/التصفير القياسية لم تتغير؛فرق amcheck في extensions_parameter_overrides موثق كاقتراح فقط.

## استثناء المالك: تمثيل ACL لتسلسلين محليين فقط

بعد الاسترجاع الصارم وقبل لقطة RESET، يطابق سكربت الاختبار فقط تمثيل صلاحيات المالك للتسلسلين `public.deferred_cheque_number_seq` و`public.inventory_movement_mutation_seq`. يشترط أن المصدر يحفظ `postgres=rwU/postgres`، والمالك postgres، وأن الحقوق الموسعة مطابقة قبل الإجراء. إذا كان تمثيل النسخة NULL، ينفذ داخل الحاوية وحدها `GRANT SELECT, UPDATE, USAGE` للمالك postgres؛ لا مستفيد آخر ولا صلاحية إضافية. أي حالة أخرى تُرفض. يقارن الكتالوج الكامل والأدوار والعضويات وبصمات البيانات قبل/بعد، ولا يقبل فرقاً غير تمثيل هذين الصفين. التكرار بلا تغيير.

**أثر يوم التشغيل:** التحقق من ACL في verify-only يوسع NULL إلى صلاحيات المالك الافتراضية، لكن المقارنة النهائية في RESET حرفية، فلا يكفي نجاح verify-only وحده. جرد فرانكفورت المحفوظ وإعادة البناء الكاملة من 180 migration كلاهما يحفظان التمثيل الصريح للتسلسلين. migrations113 و190 تنشئهما وتحدد المالك وتسحب صلاحيات الأدوار الأخرى؛ محاكاة الأرشيف الحقيقي يجب أن تثبت أن التمثيل بعد إعادة البناء يطابق المصدر حرفياً. لم تتغير مقارنة RESET أو نواته أو Restore الافتراضي أو أدوات المالك. هذا استثناء محلي محدد اعتمده المالك، وليس تعديل صلاحيات في فرانكفورت أو استثناء مقارنة.
