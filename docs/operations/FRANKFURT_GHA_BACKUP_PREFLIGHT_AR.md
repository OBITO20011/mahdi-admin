أُعيد بناء PR47 على main `b1789e1e973b7ca42dcea850f69d28a5b63cc3db` بعد دمج PR48. نطاقه النهائي تخفيف تكرار CI وتوثيق القرار فقط. أُزيلت سكربتات تجربة الدور وworkflow تشخيصه من فرق التسليم؛ تبقى خلاصة الأدلة المنقّحة في [ملف الإثبات](FRANKFURT_GHA_BACKUP_PREFLIGHT.json). لا اتصال بأي مشروع أو R2 ولا نشر أو تفعيل.

## ما يعمل الآن وما لا يعمل

- تبقى مهام Windows الخمس على جهاز المالك كما هي، مع اللحاق عند تشغيل الجهاز. لم تُحذف أو تُعدّل أو تُسجّل هنا.
- النسخ والتشفير والاسترجاع الصارم والرفع إلى R2 والاحتفاظ لا تتغير. الدليل التنفيذي الحالي: [RUNBOOK النسخ والاسترجاع](FRANKFURT_BACKUP_RESTORE_RUNBOOK_AR.md).
- عندما يكون الجهاز مطفأً لا يوجد بديل سحابي ينفّذ النسخ أو الحارس. لا يُدّعى وجود مراقب فوات مستقل 26 ساعة.
- يراجع المالك حداثة النسخة والرفع وVerifyRemote وRestoreRemote وStatus قبل يوم القطع. تبقى بوابة نجاح النسخ والاسترجاع خلال 24 ساعة كما في [خطة التشغيل §1](GO_LIVE_CUTOVER_AR.md)؛ إن تأخرت النسخة يشغّل جهازه ويتحقق قبل المتابعة.
- تنبيهات الشغل السيرفرية في 217 مستقلة عن النسخ السحابي، وتبقى محجوزة حتى يوم التشغيل. التنبيهات التقنية تبقى للمطوّر.

## لماذا لم يُقبل دور النسخ

هذه **نتائج قاعدة Supabase اصطناعية محلية حتى 217/179**، وليست فحص صلاحيات فرانكفورت الحية:

| التجربة الفعلية | النتيجة |
|---|---|
| `pg_read_all_data` وحده دون BYPASSRLS | يفشل dump كامل جداول RLS؛ لا تُقبل نسخة ناقصة |
| إنشاء LOGIN مع BYPASSRLS بواسطة postgres غير superuser | نجح محلياً؛ لم تُنشأ كلمة أو دور على مشروع حي |
| SELECT محدودة يمنحها postgres | يفشل دخول `auth` بـ42501؛ يفشل dump الكامل |
| منع INSERT/UPDATE/DELETE/TRUNCATE وDDL الدائم وإنشاء الأدوار ودالة كتابة تحت الدور المحدود | مرفوضة بـ42501 |
| TEMP تحت الدور المحدود | متاح؛ لذلك لا يُدّعى منع كل DDL |
| إضافة `pg_read_all_data` إلى دور BYPASSRLS | ينجح dump، لكن يصل الدور إلى cron وVault ويقبل حذف سجل cron وجدولة مهمة؛ تجارب الكتابة أُرجعت محلياً |
| إعادة تمثيل منح PUBLIC من الجرد المحفوظ | تؤكد قبول حذف سجل cron وجدولته في التجربة |
| `pg_dumpall --roles-only --no-role-passwords` في الفحص الأول | ناجح؛ لا كلمات مرور أدوار في الدليل |

**اكتمال تجربة التشخيص لا يعني قبول التصميم.** لا تحقق هذه المحاولة شرط دور قراءة بلا كتابة مباشرة أو غير مباشرة. لا يُستعاض عن فشلها بكلمة postgres في GitHub، ولا يُعتبر `default_transaction_read_only` عزلاً للصلاحيات، ولا تُحذف auth أوstorage أوcron من النسخة أو تُخفف مقارنة الاسترجاع.

المصادر الرسمية تشرح حدود الأدوار والمنح الموروثة؛ نتيجة منح فرانكفورت الحية لم تُتحقق هنا: [Supabase: cron وVault وPUBLIC](https://supabase.com/kb/troubleshooting/revoking-privileges-on-storage-pg_cron-vault-and-extension-objects-has-no-effect)، [PostgreSQL: الأدوار القرائية وRLS](https://www.postgresql.org/docs/17/predefined-roles.html).

## ما يتطلب اعتماداً مستقلاً لاحقاً

إعادة دراسة النسخ خارج جهاز المالك بعد التشغيل، مثلاً مع Supabase Pro أو تصميم تصدير قرائي محروس، مع إثبات صلاحيات ونسخة كاملة واسترجاع صارم. قالب المستودع الخاص لم يُنشأ؛ لا pin أو أسرار أو جدولة يلزم تفعيلها الآن. أي خطة لاحقة تحتاج اعتماداً جديداً، وتقديراً للدقائق وحارس خصوصية قبل إدخال أسرار.

يبقى [قياس CI الفعلي](GITHUB_ACTIONS_CAPACITY_AR.md) صالحاً كعينة مؤرخة، مع إبقاء جميع بوابات PR وmain. لا تُفسَّر مجانية runners العامة إذناً بوضع أسرار النسخ في المستودع العام.
